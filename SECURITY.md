# RasadTwin Security & Data Protection Policy

## Purpose

This document defines the minimum security and data-handling boundary for RasadTwin (SIH26251). It is a project-level engineering policy, not a claim of military certification, accreditation, or formal cybersecurity compliance.

## Security posture

RasadTwin is designed as an offline-first decision-support prototype for synthetic logistics scenarios. The default operating assumption is air-gapped / no-network execution.

The prototype does not perform autonomous dispatch. Recommendations are reviewed, approved, modified, or rejected by a human planner.

## Data classification

### Allowed
- Synthetic data generated by the RasadTwin simulator.
- Public, non-sensitive datasets explicitly approved by the human team.
- Public technical documentation and open-source software metadata.

### Prohibited
- Classified or restricted government / military information.
- Real unit locations or current deployment information.
- Real consumption norms, stock levels, convoy schedules, route vulnerabilities or operational capacities.
- Personally identifiable information unless clearly required and separately approved; preferably avoid it entirely.
- Credentials, tokens, API keys, private keys or internal endpoints.

### Rule
When unsure whether data is appropriate, treat it as prohibited until the human Technical Lead confirms otherwise.

## Network policy

Network access is OFF by default.

Any external network dependency requires:
1. a documented purpose;
2. an identified endpoint/service;
3. confirmation that no sensitive data is transmitted;
4. an offline fallback when practical;
5. explicit human approval.

No telemetry or background upload is allowed.

## Secrets policy

Secrets must never be:
- hardcoded;
- committed to Git;
- placed in `.env` files that are tracked;
- copied into logs;
- shown in screenshots or reports.

Use environment variables or local secret stores for development where necessary, and provide redacted examples such as `.env.example`.

## Dependency policy

Prefer open-source, pinned dependencies.
Do not add a dependency solely for convenience if a standard-library or already-approved dependency solution exists.
New network-enabled services or cloud dependencies require explicit approval.

## Application security minimums

- Validate API inputs with Pydantic or equivalent schemas.
- Reject unexpected/invalid values rather than silently coercing unsafe inputs.
- Do not expose filesystem paths, environment variables, stack traces with secrets, or internal configuration through public API responses.
- Add authentication/authorization only within prototype scope; do not pretend this is a complete military IAM solution.
- Keep audit events structured and free of secrets.
- Default CORS and network exposure to restrictive local-demo settings.
- Bind the prototype to localhost unless a phase explicitly requires a LAN demo.
- Do not expose the development server directly to the public internet.

## Logging

Logs should contain enough information to reproduce and audit behavior, but not sensitive values.
Never log credentials, access tokens, private keys or raw sensitive payloads.

## Model / AI governance

Any AI/ML module must:
- identify its model family and configuration;
- use deterministic seeds where applicable;
- keep model inputs within approved data boundaries;
- produce explainable output where required by the phase;
- never be described as autonomous command authority.

## Incident handling

If a secret, prohibited data, unexpected outbound connection, or security boundary violation is discovered:
1. STOP the affected workflow.
2. Do not delete evidence needed for investigation.
3. Record the issue in the phase report.
4. Notify the human Technical Lead.
5. Rotate/revoke exposed credentials where applicable.
6. Remove the violation only after preserving an auditable record of what happened.

## Security acceptance

A phase does not pass security review if it requires silently weakening this policy.
